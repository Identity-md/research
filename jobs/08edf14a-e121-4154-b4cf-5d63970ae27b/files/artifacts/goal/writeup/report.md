# rollup-risk: deliverable report

rollup-risk is a dependency-free TypeScript library and command-line tool that scores how trust-minimized an Ethereum rollup is from L2BEAT-style facts, explains every point, and ranks a list of rollups. It runs straight from source on Node's built-in type stripping, with no build step and no installed packages.

- Repository: https://github.com/identity-md-launches/goal-2617-build-rollup-risk-small-open-source.git
- Final trunk commit: `d8f2e544e8767dc211174ae64f011cb12458218e`

### Input and validation

The input is a JSON array. Each row has eight fields: `name` (non-empty, trimmed, unique, case-sensitive), `stage` (0, 1 or 2), `proofSystem` (`fraud`, `validity` or `none`), `permissionlessProving` (boolean), `exitWindowDays` (finite number, at least 0, fractions allowed), `upgrades` (`{ type: "securityCouncil", threshold, members }` with positive safe integers and threshold at most members, or `{ type: "multisig" }`, or `{ type: "singleKey" }`), `dataAvailability` (`ethereumBlobs`, `ethereumCalldata` or `external`) and `forceInclusion` (boolean).

The validator never coerces or mutates. It reports every independently bad field in one pass, with codes `required`, `invalid_type`, `invalid_value`, `unknown_field` and `duplicate_name` and JSON-path style locations such as `$[0].upgrades.threshold`. Unknown keys are rejected, including `threshold` on a multisig. Only a plain object counts as a row, so class instances, arrays, `Date` values and prototype tricks are rejected as `invalid_type` rather than partly accepted. An empty array is valid. Descent stops only inside a malformed container; other fields and rows are still checked.

## How the scoring works

Seven factors, scored in input-field order, with maxima that sum to 100. Each factor's reason names the observed value and the rule applied, for example "Permissionless proving is true with live 'fraud' proofs: earns 10 points."

| Factor | Max | Points |
| --- | ---: | --- |
| `stage` | 20 | stage 0: 0, stage 1: 10, stage 2: 20 |
| `proofSystem` | 20 | live fraud or validity proofs: 20; none live: 0 |
| `permissionlessProving` | 10 | 10 only when `true` and the proof system is not `none`; otherwise 0 |
| `exitWindowDays` | 15 | 0 days: 0; more than 0 and under 7: 5; 7 to under 30: 10; 30 or more: 15 |
| `upgrades` | 15 | single key: 0; multisig: 5; council with threshold 1: 0; otherwise council ratio threshold/members at least 3/4: 15, at least 2/3: 10, lower: 5 |
| `dataAvailability` | 10 | Ethereum blobs or calldata: 10; external DA: 0 |
| `forceInclusion` | 10 | `true`: 10; `false`: 0 |

The score is the integer sum. Fraud and validity proofs earn the same points on purpose, as do blobs and calldata. The council ratio is compared by cross-multiplication, so 8/12 earns 10 and 9/12 earns 15 exactly. Proof gating is the only cross-factor rule.

Ranking sorts by score descending, then by name ascending using plain JavaScript string comparison (no locale), then by original input order for exact ties. Ranks are consecutive from 1 with no shared ranks.

The README states plainly that this is a transparent heuristic, not an official L2BEAT assessment: factors overlap, the stage is supplied rather than inferred, and the model leaves out implementation bugs, council independence, emergency upgrade routes, DA design details and force-inclusion delays.

## The example and its output

`examples/rollups.json` holds six well-known rollups from an L2BEAT snapshot read 2026-10-27:

| Rollup | Stage | Proofs | Permissionless | Exit days | Upgrades | DA | Force inclusion | Score |
| --- | ---: | --- | --- | ---: | --- | --- | --- | ---: |
| Arbitrum One | 1 | fraud | true | 10 | council 9/12 | blobs | true | 85 |
| OP Mainnet | 1 | fraud | true | 0 | council 10/13 | blobs | true | 75 |
| Base | 1 | fraud | true | 0 | council 8/11 | blobs | true | 70 |
| Starknet | 1 | validity | false | 7 | council 9/12 | blobs | false | 65 |
| ZKsync Era | 0 | validity | false | 5 | council 6/8 | blobs | false | 50 |
| Scroll | 0 | validity | false | 0 | multisig | blobs | true | 45 |

Arbitrum One's 85 is 10 + 20 + 10 + 10 + 15 + 10 + 10 in factor order. Base's council ratio 8/11 is about 0.727, at least 2/3 but under 3/4, so it earns 10 upgrade points.

The CLI prints this table for that file, and `examples/expected.txt` holds exactly these bytes:

```
Rank  Rollup        Stage  Score
1     Arbitrum One  1      85
2     OP Mainnet    1      75
3     Base          1      70
4     Starknet      1      65
5     ZKsync Era    0      50
6     Scroll        0      45
```

The README reproduces the full input JSON (identical to `examples/rollups.json`) and this table (identical to `examples/expected.txt`). The `--json` output, a pretty-printed array of ranked rollups with every factor's points and reason, is committed as `examples/expected.json` and linked from the README rather than pasted into it.

## How to run the tool

Clone the repository and use Node 24 or newer. Nothing to install, nothing to build.

```
git clone https://github.com/identity-md-launches/goal-2617-build-rollup-risk-small-open-source.git
cd goal-2617-build-rollup-risk-small-open-source
node src/cli.ts examples/rollups.json          # ranked table
node src/cli.ts --json examples/rollups.json   # JSON with factor breakdowns (flag works on either side)
node src/cli.ts --help                         # usage, exit 0
npm test                                       # node --test test/*.test.ts
```

Behaviour of the tool:

- Success writes only to stdout and exits 0. A table has `Rank`, `Rollup`, `Stage` and `Score` columns padded to the widest value. JSON is `JSON.stringify(ranked, null, 2)` plus a newline.
- An empty array prints a header-only table, or `[]` with the flag.
- No argument, an unreadable file, malformed JSON or invalid rows write the problem to stderr, print nothing on stdout and exit 1. Validation failures list every bad field, one `$[i].path: message` line each.

As a library:

```ts
import { validateRollups, scoreRollup, rankRollups } from './src/index.ts';
const result = validateRollups(JSON.parse(text));
if (!result.valid) { for (const e of result.errors) console.error(e.path, e.code, e.message); }
else { for (const r of rankRollups(result.rollups)) console.log(r.rank, r.rollup.name, r.score, r.factors); }
```

## What is missing or limited

- The six-rollup facts are a snapshot read from L2BEAT on 2026-10-27 by the research item. The documentation workers recorded them as supplied and did not re-verify them live, and `docs/example-sources.md` says so. L2BEAT and the rollups change, so the example will go stale.
- Known modeling simplifications, all documented in the README and the sources document: exit windows are regular-path values and all six rollups have emergency paths with no window; council thresholds describe the council Safe alone and leave out co-signers; Base is recorded as `fraud` with permissionless proving although L2BEAT describes a hybrid TEE plus ZK system since June 2026 (the orchestrator's wave-4 brief wrongly called it a validity label, both docs workers noted the mismatch, and either label earns the same 20 points); Scroll is upgraded by a 3-of-4 team multisig since 2026-06-01 and can disable enforced batches, so its `forceInclusion: true` is conditional; ZKsync Era's priority queue and Starknet's council minority are not counted as forced inclusion.
- The score is a fixed, transparent heuristic, not an official L2BEAT assessment. Stage is an input, not derived from the other factors, so a row can carry an inconsistent combination and still score.
- The trunk was verified on Node 24.21.0, 24.22.1 and, for this report, 22.23.3, not on every Node 24 patch release. Type stripping is a Node feature, not something the package controls.
- The README shows the table output; the JSON output lives in `examples/expected.json` rather than being reproduced inline.
- The package is not published to npm and is meant to be run from a source checkout. There is no `tsconfig`, linter or CI configuration, by design: the requirement was no dependencies and no build step.
