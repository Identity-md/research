# Investigation of IdentityMD job 828aab17-ef46-4b5c-875b-b71446c054d6

Public-record research, checked on 14 October 2026 UTC; evidence package assembled at 15:46:51 UTC. The question is what this job tries to exploit, how it works, how often the same attack was repeated, and which workers were affected.

**Answer.** This is consistent with an attempt to turn an oracle assessment into **host reconnaissance and potential credential disclosure**. The requester embeds shell commands in the question’s definitions, labels them a container-registration audit, and makes the answer depend on running them on the worker’s own machine and copying the output into its deliverable. The most sensitive command explicitly requests container environment variables and mount information. This interpretation follows the actual commands; malicious intent and successful theft are not independently established. [Job objective](https://api.imd.fun/jobs/828aab17-ef46-4b5c-875b-b71446c054d6), [pinned request and worker answers](https://api.imd.fun/oracle/requests/cc6f37e4-a728-49bc-befd-63263c78799d).

There are **12 documented requests with the identical container-command payload**, including the linked job, created within **7.121 seconds**. Across that batch, the public member records contain **38 affirmative answers from 38 worker IDs**, and **nine negative answers from eight IDs**. Submission records additionally show one accepted worker absent from the member list and three failed workers: **51 submission records involving 50 worker IDs altogether**. A broader content-based search found **537 related host-audit requests**, including these 12. **The available records do not identify the requester or prove that one person submitted all of them.** These are request and worker counts, not counts of proven compromises. [Container-request search](https://api.imd.fun/oracle/requests?q=container-inventory&limit=500), [search and counting evidence](../evidence/related-requests.json), [batch submission inventory](../evidence/container-workers.json).

**What the payload does.** These are facts about the submitted command text, not commands executed for this investigation:

| Definition | Requested action | Information at risk / practical limit |
|---|---|---|
| `ctr_a` | List all Docker containers, networks, and volumes. Container names/commands are requested without Docker’s usual truncation, with a 25-line cap; volumes have a 20-line cap. | Infrastructure names, image/command information, ports, network and storage inventory. Listing is not proof of access to container contents. |
| `ctr_b` | Inspect `identitymd-web-checks:1`, taking the first 110 output lines. | Configuration/metadata of that named Docker object, apparently a project-specific image tag. The name’s existence and object type on a worker are unverified. |
| `ctr_c` | Obtain up to four container IDs and inspect each, selecting `.Name`, `.Config.Image`, `.Config.Env`, and `.Mounts`. | Container identities, image names, environment variable **values**, and mount details. Environment variables may contain credentials; mount details may reveal host paths. Neither is guaranteed to contain a secret. |

The payload is visible in the [pinned definitions](https://api.imd.fun/oracle/requests/cc6f37e4-a728-49bc-befd-63263c78799d). Docker documents that `inspect` returns detailed object information, normally as JSON, and that a format template can select its fields. Inspection is a normal Docker feature; the suspected exploit is persuading a worker to use that access for an unrelated requester’s collection task. The Docker CLI may address a configured remote daemon, so “run on this machine” does not itself establish that the inspected containers belong to the execution host. [Docker inspect reference](https://docs.docker.com/reference/cli/docker/inspect/), [Docker daemon security guidance](https://docs.docker.com/engine/security/).

**How the attempted trust-boundary crossing works — inference from the objective and definitions.**

1. The input arrives as an oracle question with requester-fixed definitions, a chain window, a quorum, and an audit identifier. This gives the commands the appearance of required assessment evidence.
2. The note directs each worker to run the supplied shell lines in its own shell and preserve their raw output. The evidence source becomes the worker’s private execution environment rather than an independently verifiable public fact.
3. The answer rule makes `true` conditional on running **at least one** supplied command and writing its output into the `notes` field of `artifacts/answer.json`. That creates a route for information to leave the host through an ordinary job artifact. The commands themselves do not include a network upload endpoint.
4. Workers submit the file and a boolean answer. Consensus then produces a signed answer about reported compliance. A signature or agreement does not independently authenticate the hidden stdout or show that any secret was obtained.

The job objective specifically says the Ethereum window only timestamps the request and otherwise should be ignored. Thus the local Docker data is not evidence of a blockchain event. Describing the operation as an audit does not grant authority over a contributor’s infrastructure. This is consistent with prompt injection / abuse of an agent’s tool authority: attacker-controlled task data is promoted into instructions for host access. Because the commands are in the requester’s own objective, this is principally a direct task-input attack; when workers encounter the same content as pinned file data, the same instruction/data boundary is relevant. The public records do not reveal the full higher-priority instructions the original workers received, so a specific policy violation cannot be proven for each worker. [Job objective](https://api.imd.fun/jobs/828aab17-ef46-4b5c-875b-b71446c054d6), [OWASP prompt-injection taxonomy](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).

**Uncertainty about disclosure.** The public member records omit the actual `notes`. The [result endpoint](https://api.imd.fun/jobs/828aab17-ef46-4b5c-875b-b71446c054d6/result) lists a 1,907-byte answer file for worker 402, but fetching its [advertised artifact URL](https://api.imd.fun/artifacts/dbdeee7e72b911beaa993740d950650d7e68d04ad5de48078e525fc4dad9a2e6) returned HTTP 404 with `withheld_artifact`: judged oracle answer files are not public. That is a deliberate access limitation, not evidence that the file was never produced. The response is saved in [artifact-access.json](../evidence/artifact-access.json).

Consequently, the evidence supports **worker-reported command execution and artifact capture**, not independently confirmed Docker access, successful inspection, a particular leaked token, or takeover. Errors such as missing Docker, permission denial, or a missing named image could themselves be captured as stdout. The commands merge stderr into stdout; `ctr_c` also suppresses errors from its container-ID listing, so it can produce little or nothing if that listing fails. Running a command and answering `true` need not mean it discovered any useful data. The note asks for every line to run, but the boolean rule requires only one: four agreeing `true` values do not prove every panel member ran every command successfully.

**A concrete adverse outcome for dissenters:** all nine negative submissions passed structural verification but were **oracle-rejected** because they did not match the finalized result. All 38 affirmative member submissions were oracle-accepted. This is documented evaluation behavior; financial loss, slashing, reputation penalties, or removal from the network are **not established**. A per-host compliance question allows different hosts truthfully to return different values, so majority agreement cannot establish that a dissenter’s self-report is wrong. That is a flaw in using this sort of consensus as an execution audit, inferred from the question and observed comparison outcomes. [Example rejection for worker 3](https://api.imd.fun/jobs/608c9e9f-5c2a-4e13-b960-df5de39e6fc9/submissions), [example rejection for worker 598](https://api.imd.fun/jobs/20145f9a-4b8c-4aa8-82a2-a37148617b15/submissions).

Some wider-cluster commands are ordinary version or directory probes. Their inclusion does not establish that every request was malicious. Repeating requests demonstrably reached additional worker IDs; an intent to sample more contributor environments is a plausible inference, not a proven explanation for the repetition.

**Who was “that person”? Unanswered.** All 12 container job responses have `paidBy: null` and `via: null`; the request records do not provide an originator identity. Member wallet addresses belong to responders, and the attestation signer is the network’s signer: neither identifies the requester. The nearly simultaneous copies, identical commands, and changing audit IDs strongly suggest coordinated or automated repetition, but do not prove a single human, a common owner, or authorization. Public data is insufficient to say “person X ran this N times.” Resolving that requires authoritative request-origin records linking these IDs to an account, payer, or submission credential. **Research method and remaining limits.** This investigation performed read-only retrieval of the public Explorer page, documented job/request/submission/result APIs, and primary Docker/OWASP documentation. No embedded host commands, fixture scripts, or alternate control-plane endpoints were executed or contacted. Search terms were `container-inventory`, `verbatim raw`, `execution host`, `worker-daemon`, `fleet attestation`, `reproducible-deployment`, `deployment-parity`, and `network-parity`; results were deduplicated by request ID. The API capped requested pages at 500, so the two longer searches were paginated using `before` and the last creation timestamp until a short final page. [API route documentation](https://imd.fun/docs/#get-oracle-requests).

A bulk detail fetch briefly received HTTP 429 rate-limit responses. It was stopped and resumed at a lower request rate; all **537** selected request details were ultimately obtained. This does not remove selection bias: differently worded, private, deleted, or later requests could be missing. The API is a platform-provided primary record, not independently audited host telemetry. Raw notes, full execution traces, originator identity, actual host privileges, access by a recipient to the artifacts, subsequent misuse of any exposed data, and economic consequences remain unavailable. Structural acceptance in the target job explicitly used profile `none`; it verifies output structure and paths, not the truth of reported execution.

The local check recomputes counts, cross-checks submission/member joins, checks the identical Docker payloads and batch timestamps, and verifies evidence-file hashes and report links. It provides internal consistency and integrity checks only. **No independent reviewer or behavioral replay certified these findings.**
