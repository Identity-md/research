# Can developers use a public agent swarm privately?

**Research date: 1 November 2026.** Public information only; no accounts created, teams contacted, jobs submitted, services purchased, or private code requested.

## Group-chat summary

IMD could offer useful privacy without hiding work from the agents doing it. The smallest worthwhile change is a private project whose brief, files, reviews and results are readable only by its customer and authorized builders, reviewers and operators. Hiding it from Explorer alone would not achieve that: sampled IMD APIs expose the brief, attempts, source bundles, results and project history without login. Payments and receipts can remain public without publishing those contents. Keeping secrets even from workers is a separate, substantially harder feature: confidential-computing systems demonstrate pieces of it, with important trust and tooling limits. Make public showcases a separate, customer-approved release. This is a technical opportunity, not evidence that customers will pay a particular premium.

## How to read the evidence

**Observed**: public response or distributed code inspected here. **Documented**: provider-described availability, not independently tested enforcement. **Roadmap/historical**: separate from current features. **Inference/proposal**: this report's reasoning. **Unknown**: not established publicly. Availability means public onboarding/tooling exists, not an end-to-end certification.

Three different promises matter:

1. **Explorer-hidden:** removal from a website; other public surfaces can still reveal the job.
2. **Access-restricted:** contents/results restricted to the customer and explicitly authorized participants. Workers, reviewers, operators and any receiving AI/tool providers remain trust dependencies.
3. **Worker/operator-confidential:** sensitive data stays inside an approved protected execution boundary, including its input, storage, inference and output paths. Attestation, encryption and authorization must work together. A private repository or a content hash alone provides no such execution protection.

**What these comparisons establish:** central services and self-hosted systems show that multi-agent collaboration need not entail public publication. Open networks require separate scrutiny of task transport, downloadable assets and worker trust. Confidential infrastructure supplies useful components, not an automatic confidentiality guarantee for a complete agent workflow. This is an inference from the boundaries above.

**Existing controls are narrower than privacy.** Documentation offers GitHub/IPFS publication switches, accepted files as subsequent-job inputs, and owner-checked continuations. It also describes Venice-backed jobs as keeping work private. These do not establish restricted job reads or confidential worker execution. [IMD documentation](https://imd.fun/docs/)

**Provider exposure is separate.** Venice offers several privacy modes. IMD's inspected gateway sends ordinary chat requests; its documented E2EE flow was not identified there. Protected inference alone would still leave worker files and IMD delivery paths exposed. [Venice modes](https://docs.venice.ai/overview/privacy), [E2EE protocol](https://docs.venice.ai/guides/features/tee-e2ee-models), [pinned IMD gateway code](https://github.com/Identity-md/worker/blob/5ca326863d37fccae728b89012aa28fb55afcfe6/dist/cli.js)

**Explorer hiding:** reduces casual discovery and indexing. It does not retract already published data, block direct API/bundle/artifact reads, hide source repositories/IPFS copies, erase chain input, or constrain workers and model providers. A nonlisted URL is not authorization. Private work across iterations needs project-wide access rules covering every parent, dependency, retry, review and export.

## Prioritized recommendation

**Start with Level 2 private projects for pre-launch work.** This is an engineering proposal, not a claim that IMD already supports it. It addresses individual developers' immediate concern—public exposure of unfinished mechanics and research—while stating clearly that authorized workers, operators and approved inference/tool providers can read the work.

| Option | User benefit and remaining trust | Changes and verification consequences | Burden and limits |
|---|---|---|---|
| **1. Explorer hiding** | Less browsing/search exposure; everybody with another public route may still read. | Filter listings, detail previews, search, feeds and caches consistently. Does not change execution/verification. Label it **unlisted**, not private. | Low relative effort; old caches, APIs, repositories and chain records remain. Useful presentation control only. |
| **2. Public-access restrictions — first priority** | Prevents internet users and unassigned workers from retrieving contents. Trust assigned builders/reviewers, platform operators and declared providers. | Project ACLs, lease-scoped fetches, private artifact storage/source delivery, redacted receipts/logs, explicit retention, publication gating. Re-run checks and restricted panels can continue; public readers lose independent access to full evidence. | Moderate, cross-cutting backend/worker/product work. Copies already read cannot be recalled; operator compliance and provider terms matter. |
| **3. Worker/operator-confidential execution — later pilot** | Reduces trust in compute hosts for selected workloads; still trusts measured software, hardware, key governance and authorized output recipients. | Attested worker **and verifier**, protected inference, key release bound to approved measurements, encrypted state/results, controlled egress/logging and upgrades. Attestation proves a boundary/configuration, not that the research conclusion or generated code is correct. | High integration and operations burden; narrower hardware/models/tools, side channels, software exploits, outages and metadata leakage remain. Not a drop-in property of the present worker. |

### Proposed private-job lifecycle

1. **Create a private project.** Authenticate the customer; select authorized roles and allowed model/tool providers. Store brief, source and attachments in encrypted off-chain storage with a project ACL. Use opaque identifiers and nonsensitive public labels. Enforce privacy on the server.
2. **Pay against a commitment.** Keep the brief out of chain calldata/events. Adapt the existing quoted-payment pattern, admission and delivery paths. Commit to a randomized private manifest; salt low-entropy content hashes to resist guessing and linkability.
3. **Assign before disclosing.** Advertise capabilities and coarse workload only. Give selected builders/reviewers/verifiers short-lived, identity-bound fetch grants for required inputs. Reauthorize replacements. Disclose that authorized independent workers can copy plaintext; record access.
4. **Execute and check privately.** Restrict workspaces, logs, summaries, screenshots and previews. Enforce approved inference/tool policies instead of assuming every personal subscription has suitable settings. Preserve the actual verification level in receipts.
5. **Deliver without publishing.** Return a versioned manifest and authenticated downloads or a private repository. Publish minimal receipts/commitments; keep detailed evidence restricted. Never place a bearer download credential in an on-chain URI.
6. **Continue privately.** Inherit ACLs, provider rules and artifact permissions across jobs. Block private-to-public attachments by default. Approve new participants, expire fetch grants, clean worker copies and document backup/provider retention exceptions.
7. **Publish a separate release on request.** Preview selected files/text, scan for private history and secrets, obtain customer consent, then export the showcase/repository/site. Earlier briefs, attempts and versions stay private unless approved separately. Published copies cannot reliably be recalled.

**Verification/disputes:** minimal on-chain commitments are technically plausible because the inspected contracts accept hashes/URIs rather than interpreting the evidence. This does not establish compatibility with every IMD server schema or reward policy. Keep a restricted evidence bundle for a defined dispute window and give explicitly authorized adjudicators access. If IMD intends permissionless public challenges, hiding evidence changes that assurance; do not quietly replace it with an operator's assertion. For deployed public contracts and public oracle answers, the deployed bytecode/transactions or answer itself remains visible even when preparatory work is private.

**Today:** use the sampled IMD path for deliberately public or sufficiently redacted work; keep sensitive core work in a controlled workflow until a restricted mode is shipped and tested.

**Demand/pricing:** the compared products demonstrate privacy supply, not quantified IMD demand. This brief and public research jobs establish use cases, not willingness to pay. Pilot private projects and measure adoption/costs; no evidence here supports a revenue uplift or specific surcharge.

## Five questions for IMD maintainers

1. Does any supported private-project mode already exist, and exactly which read APIs, artifact stores, history routes, receipts and Explorer caches enforce its ACL?
2. Who can receive full task/dependency contents internally—assigned workers only, standby/replacement workers, planners, reviewers, verifiers, operators—and can customers approve or constrain that set?
3. What are actual retention, deletion, backup, logging and model-provider/training policies across these actors, including Venice model selection and any provider fallbacks?
4. Which current acceptance, reward, reputation or dispute rules require public evidence, and could private jobs retain the same rewards with restricted adjudication and accurately labeled verification?
5. Can private source/artifact delivery, inherited project permissions and an explicit later publication step be supported without automatic GitHub/IPFS/receipt-content publication, and what migration is needed for existing clients/contracts?

## Appendix A — Platform evidence and important limitations

### A1. Olas: off-chain is not automatically private

**Documented standard implementation:** request JSON includes `prompt`, `tool` and a nonce; the requester uploads it to IPFS. Mech watches request references, reads the payload, calls its tools, and uploads a response to IPFS. Referenced readable content is exposed to anyone obtaining it; hashing does not encrypt it. This is stronger evidence than assuming a decentralized marketplace must either be private or public. [Mech tool-development documentation](https://stack.olas.network/mech-tools-dev/)

**Current transport update:** September's rollout describes direct HTTP requests with asynchronous on-chain settlement. The current client allows inline off-chain answers as well as IPFS delivery. Thus it would be wrong to claim every current off-chain prompt/result must be published to IPFS. Neither source establishes a marketplace-wide ACL, confidential execution, deletion schedule, private iteration store or customer-controlled publication contract. Operator terms and actual tool behavior must be checked. [Rollout](https://olas.network/blog/cheaper-faster-off-chain-requests-mech-marketplace), [client return semantics and operator disclosures](https://stack.olas.network/mech-client/)

**Exposure/retention:** an executing Mech sees inputs and intermediate work; its upstream model/tool services see what it sends. Published references, payment histories and third-party IPFS copies cannot be treated as privately revocable storage. Private chained work is therefore **not established**, although a custom operator could implement it. No verified global retention or privacy-price schedule was found.

### A2. Golem: useful separation of compute and delivery, with public-image hazards

**Documented:** the requestor sends code/data to a selected provider and downloads results. This does not require publishing a finished product. However, the VM-image guide requires images named in demands to be public and describes provider-host-backed volumes. It also documents filesystem continuity across tasks within an activity. **Inference:** a generic public runtime plus separately transferred inputs avoids publishing secrets in the image, but does not protect them from its host administrator. [Transfer examples](https://docs.golem.network/docs/creators/javascript/examples/transferring-data), [image requirements and filesystem behavior](https://docs.golem.network/docs/creators/javascript/guides/golem-images)

**Access/storage qualification:** the published GFTP implementation binds download handlers to a file-content identifier; no per-assigned-worker ACL check was identified in those handlers. This is static inspection, not a live network authorization test, and is another reason not to label the whole network Level 2. Transfer URLs should be treated as sensitive. [GFTP implementation](https://github.com/golemfactory/yagna/blob/main/core/gftp/src/gftp.rs)

The provider FAQ documents configurable task cleanup, defaulting to 30 days; that is not cryptographic erasure or a guarantee against copies. Providers have local logs, while pricing/node/payment information is available publicly. An application calling an external LLM adds that provider; Golem itself is compute infrastructure, not a compulsory model broker. No universal retention contract or managed private-project/publication feature was established. [Provider FAQ](https://docs.golem.network/docs/providers/provider-faq), [debug logging](https://docs.golem.network/docs/creators/python/guides/debugging)

### A3. Devin: account privacy still includes operator and provider trust

**Documented:** repository access is selected through the GitHub integration; resulting PR visibility follows the repository. Central managed sessions coordinate multiple VMs, rather than independent third-party seat holders. Session tools expose commands, edits and browser activity to the customer. Continued work can use the same private repository and organization context. [GitHub permissions](https://docs.devin.ai/integrations/gh), [managed Devins](https://docs.devin.ai/work-with-devin/advanced-capabilities), [session tools](https://docs.devin.ai/work-with-devin/devin-session-tools)

Security docs describe encrypted transmission/storage and limited production access by role. They also say training may occur by default; paid customers may opt out, enabling ZDR with model providers, while enterprise training requires express consent. Retention of service data and some feedback/interaction data differs. **Do not interpret ZDR at model providers as deletion of the hosted project or session history.** [Security and data controls](https://docs.devin.ai/admin/security)

The DPA lists infrastructure/logging and model subprocessors, including OpenAI and Anthropic, and provides a termination-related deletion period with exceptions. The general privacy notice warns about shared conversation links. Repository choice does not control all integrations, central logs or legal retention. Self-serve access is documented; stronger enterprise deployment terms are not a universal free-tier entitlement. No separately itemized privacy-only premium was established. [DPA](https://cognition.com/legal/data-processing-statement), [privacy notice](https://cognition.com/legal/privacy-policy), [plan structure](https://cognition.com/blog/new-self-serve-plans-for-devin)

### A4. CrewAI: keeping work private is the deployer's responsibility

**Documented implementation surface:** the OSS framework supports agent orchestration and local models. Storage, authentication, file permissions and tool access depend on the deployment; installing a framework does not supply an independent-worker labor pool or a privacy contract. [Framework README](https://github.com/crewAIInc/crewAI)

Telemetry collects technical attributes including tool names and agent roles; those names can themselves disclose a project. `share_crew` enables richer data sharing. Current docs distinguish `CREWAI_DISABLE_TELEMETRY` from tracing controls: `OTEL_SDK_DISABLED` does not disable AMP tracing, which needs its own setting. [Telemetry controls](https://docs.crewai.com/en/telemetry)

Trace docs describe upload consent/authenticated exports and warn that traces can contain prompts, inputs and outputs. Hosted tracing is another recipient when enabled. Private iterations can use local or customer-controlled memory/state; persistence and embeddings may add further service dependencies. **Inference:** customers can avoid public disclosure with local models, controlled tools, disabled exports and secured storage, but remain responsible for backups/deletion and administrator access. No universal retention duration applies to every self-hosted configuration. [Trace export behavior](https://docs.crewai.com/en/observability/tracing), [memory configuration](https://docs.crewai.com/en/concepts/memory)

### A5. iExec: protected data and execution do not make every layer secret

**Documented current workflow:** DataProtector authorization selects permitted apps/users; the SMS checks the protected workload's eligibility before releasing secrets. Trusted application code sees decrypted inputs and intermediates inside its execution boundary. External AI services still receive any plaintext that application sends them. A malicious authorized app can intentionally disclose data: permission must be to reviewed behavior, not merely an app address. [Access control](https://docs.iex.ec/guides/manage-data/manage-access), [confidential assets/SMS](https://docs.iex.ec/guides/build-iapp/advanced/access-confidential-assets)

**Critical qualification from implementation:** the public SMS README describes AES-encrypted disk storage, TLS provisioning, a local encryption-key path and separate TEE provisioner/session-storage services. That does not establish that every production SMS operator is excluded from secret access. Current high-level docs mention TEE-backed secret storage; the deployed configuration was not verified. Therefore this report credits a conditional protected-worker path, **not proven confidentiality from all infrastructure operators**. [SMS source and configuration](https://github.com/iExecBlockchainComputing/iexec-sms)

**Results/public residue:** SDK instructions explicitly request `--encrypt-result` and use a beneficiary encryption key; do not assume all task outputs are secret by default. The input guide distinguishes public `inputFiles` URLs and on-chain arguments from protected data/secrets. Asset schemas, identities, orders and prices also reveal metadata. Confidentiality of application source/container distribution was not established; protected input data alone does not establish private application code. The Explorer includes result-download and encryption-status views. [Encryption tutorial](https://docs.iex.ec/guides/build-iapp/advanced/protect-the-result), [arguments warning](https://docs.iex.ec/guides/use-iapp/run-iapp-with-ProtectedData), [Explorer](https://docs.iex.ec/get-started/tooling-and-explorers/iexec-explorer)

Reusable authorizations and protected datasets support repeat computations. Re-protecting derived state and controlling who can run which application would be needed for a private iterative swarm; this was not verified as a packaged feature. No firm general dataset/result deletion schedule was established; revoking future use cannot retract previously delivered plaintext. Workerpool onboarding currently points prospective operators to assistance, so do not equate the public requester toolkit with frictionless permissionless joining of its current TDX fleet. [Workerpool documentation](https://docs.iex.ec/get-started/overview/workerpool)

### A6. Phala/dstack: inspect the whole chain of trust

**Actual implementation surface:** deployment and attestation guides, client-side encrypted secrets, GPU verification commands and open-source dstack provide more than a marketing claim. The secret guide specifies client-side encryption to values decryptable in the CVM and warns that logs or Terraform state can expose them. [Encrypted secrets](https://docs.phala.com/phala-cloud/cvm/set-secure-environment-variables), [attestation](https://docs.phala.com/phala-cloud/getting-started/attestation), [dstack implementation](https://github.com/Dstack-TEE/dstack)

**Boundary:** customer-approved code inside the CVM can read inputs, source and outputs. Excluding a host does not exclude a developer/operator with authorized SSH, logging access or power to approve malicious code. Cloud KMS policy remains controlled by Phala; on-chain KMS can make update authorization externally visible and configurable. It does not automatically remove every governance/key compromise risk. [KMS governance](https://docs.phala.com/phala-cloud/key-management/cloud-vs-onchain-kms)

The Private AI API documents gateway plaintext processing, varying upstream evidence coverage and explicit client verification. It warns that local agent tools and telemetry are outside its inference boundary. Thus attesting a gateway is insufficient evidence of an entire confidential swarm. Dedicated GPU TEE deployments provide more control over serving code but require actual workload/CPU/GPU/channel verification. [Inference trust boundary](https://docs.phala.com/phala-cloud/confidential-ai/confidential-model/trust-boundary), [GPU guide](https://docs.phala.com/phala-cloud/confidential-ai/confidential-gpu/deploy-and-verify)

**Storage/retention/publication:** protected application storage and keys can preserve private state across runs; application authentication and encrypted result delivery still have to be implemented. Public Logs explicitly allows unauthenticated access to a copied URL when enabled; disable it for sensitive workloads. There is no single retention promise established here for every customer-built application's files, backups and logs. Hardware allocation, billing/traffic metadata and public attestations or governance transactions can remain visible without revealing content. [Log controls](https://docs.phala.com/phala-cloud/monitoring/public-logs), [dstack storage/key design](https://docs.phala.network/dstack/overview)

### A7. Documented limited attempts, and what was not found

- **Golem SGX/Graphene, historical prototype:** a 2019 first-party account reported working Blender integration but said both integration and LibOS needed more development before mainnet. The SGX runtime repository contains voting-demo work and unresolved release/driver issues. This documents attempts and incomplete integration, **not a verified abandonment decision**. No reliable first-party explanation that privacy failed commercially was found. [2019 engineering Q&A](https://blog.golem.network/q-a-with-piotr-janiuk-part-ii-intel-sgx-gnt-and-more/amp/), [runtime repository](https://github.com/golemfactory/ya-runtime-sgx), [release issue](https://github.com/golemfactory/ya-runtime-sgx/issues/12), [driver issue](https://github.com/golemfactory/ya-runtime-sgx/issues/11)
- **iExec SGX compatibility limits:** its account of moving toward TDX says SGX applications could require substantial rewriting. The current TDX guides show a successor approach; this is a documented technical limitation and evolution, not evidence the overall privacy effort was abandoned. The 2026 roadmap alone is not proof every planned capability shipped. [Compatibility discussion](https://iex.ec/blog/ai-privacy-risks-personal-data-ai-systems), [roadmap](https://iex.ec/blog/2026-privacy-roadmap)
- **Phala, explicitly residual work:** the dstack-cloud threat model lists side channels, governance collusion, service denial and a KMS root-key trust concentration; distributed MPC root-key generation is described as future work for that architecture. Do not apply a design document's stronger future trust model to every current deployment. [Threat model](https://docs.phala.com/dstack-cloud/security-model)

No substantiated abandoned **IMD private-work product** was identified in the public material reviewed. That finding does not mean nobody tried, or that one is impossible.

### B3. Additional leakage and uncertainty checklist

- **Unassigned workers:** public reads make non-assignment irrelevant for sampled contents. The lease-based submission channel does not remedy public downloads. Internal dispatch/planner visibility beyond the distributed client remains unknown.
- **URLs/repositories:** source/import URLs, presigned URLs, Git commit history, issue/PR bodies, repository names and README files can reveal the project. Private repositories only protect repository readers; workers and model services still see content they process.
- **Logs/previews:** summaries, error reports, screenshots, browser previews, tracing, content checks, search queries and external tools can export sensitive details. IMD-wide logging/access/backup retention and preview authentication were not established; these are risks to review, not claims that every listed surface currently leaks.
- **Model-provider policy:** workers' own Claude/Codex accounts are material. Ordinary hosted routes add Anthropic/OpenAI as model-context recipients; configured gateways such as Venice can change that chain (inference from the runtime paths, not a per-job routing audit). Anthropic's consumer policy explicitly covers Claude Code, allows extended retention for opted-in training, and includes safety/legal exceptions. Exact settings on IMD workers are unknown. Do not apply API enterprise terms to every personal worker plan. [Worker account model](https://github.com/Identity-md/worker/blob/5ca326863d37fccae728b89012aa28fb55afcfe6/README.md), [Anthropic consumer retention](https://privacy.claude.com/en/articles/10023548-how-long-do-you-store-my-data)
- **Venice:** available inference privacy modes do not remove customer content from IMD APIs or worker disks. An anonymized provider route still exposes prompt content to that provider; documented E2EE requires a different client flow. The inspected worker gateway does not establish that flow. [Modes](https://docs.venice.ai/overview/privacy), [gateway code](https://github.com/Identity-md/worker/blob/5ca326863d37fccae728b89012aa28fb55afcfe6/dist/cli.js)
- **Verification scope:** research/website skill metadata currently advertises a structural path without substantive checks, consistent with the sampled result manifests. Other profiles have different checks; neither acceptance nor an attestation is a blanket assurance of research truth or code safety. [Live skill catalog](https://api.imd.fun/skills)
- **Irreversibility:** removing an API route or changing permissions later cannot erase chain events, public repository history or downloaded/IPFS-replicated copies. Private mode must apply before first submission and throughout the project.

### B4. Research limits

The six comparisons intentionally cover different categories rather than treating their security claims as interchangeable. Documentation was checked against distributed code/public responses where feasible. No private account security test, paid execution, hardware attestation experiment, penetration test, backend audit or cryptographic proof of provider compliance was performed. Negative search findings about abandoned products and retention are limited to the linked public materials; they are not claims of impossibility. The accompanying checks establish file/link structure and observation consistency, not independent factual certification.
